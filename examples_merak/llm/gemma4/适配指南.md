# Gemma4 适配指南（Merak / xhmodel_merak）

## 目标

基于 `weights/gemma-4-31B-it`，完成 Gemma4 在 `examples_merak/xhmodel_merak` 体系下的适配分析与落地方案设计，明确：

1. Gemma4 模型架构与输入输出特点。
2. cache / sliding window / multimodal 组织方式。
3. 为了让整图可 trace，需要补哪些 wrap。
4. 在 `xhmodel_merak` 中最小可落地的文件拆分、注册点、验证闭环。

> 本文档聚焦 **Merak 路径**（`examples_merak/` + `xhmodel_merak/`），因为当前任务文件位于 `examples_merak/llm/gemma4/`，并且现有 Merak 模型（如 `qwen3_5` / `qwen3_vl`）已经提供了最接近的复用模板。

## 一、模型基础信息

### 1.1 权重与入口

- 模型目录：`weights/gemma-4-31B-it`
- `config.json` 中的主架构：`Gemma4ForConditionalGeneration`
- `configuration.json` 中的任务类型：`image-text-to-text`
- 当前权重的 `audio_config = null`，因此**本次实际适配范围应以图文多模态为主**，音频分支可先不落地。

### 1.2 环境约束

当前仓库默认环境：

```bash
source env.sh
conda activate xhquant
```

仓库环境里的 `transformers` 版本为：

```text
5.3.0
```

而 Gemma4 checkpoint 的配置里标注的版本为：

```text
5.5.0.dev0
```

这说明：

1. 现有环境**原生不包含** `transformers.models.gemma4`。
2. 如果直接走 `AutoConfig / AutoModelForImageTextToText.from_pretrained(...)`，会卡在 `gemma4` 架构识别。
3. 参考 `xhmodel_merak/xh_llm/models/qwen3_5/` 的做法，**更合理的落地方式不是强依赖升级环境**，而是：
   - 在仓库内 vendor Gemma4 的 `configuration/modeling/processing/image_processing`；
   - 再通过 Merak 自己的 model wrapper / register 体系完成适配。

## 二、Gemma4 架构分析

### 2.1 总体结构

Gemma4 的主模型可以拆成三部分：

1. **语言模型**：`Gemma4TextModel`
2. **视觉编码器**：`Gemma4VisionModel`
3. **多模态投影层**：`Gemma4MultimodalEmbedder`

在官方结构里：

- `Gemma4ForConditionalGeneration`
  - `model: Gemma4Model`
    - `language_model: Gemma4TextModel`
    - `vision_tower: Gemma4VisionModel`
    - `embed_vision: Gemma4MultimodalEmbedder`
    - `audio_tower / embed_audio`（当前 checkpoint 不启用）
  - `lm_head`

因此它不是“视觉特征直接拼接进文本 embedding”那么简单，而是：

1. 先用 `vision_tower` 将 patch token 编码；
2. 再用 `embed_vision` 投影到 text hidden size；
3. 最后把这些 soft token 替换到文本序列中的 image placeholder 位置；
4. 再送入 `language_model` 做自回归生成。

### 2.2 文本分支配置（来自 `weights/gemma-4-31B-it/config.json`）

核心参数：

- `num_hidden_layers = 60`
- `hidden_size = 5376`
- `intermediate_size = 21504`
- `num_attention_heads = 32`
- `num_key_value_heads = 16`
- `head_dim = 256`
- `num_global_key_value_heads = 4`
- `global_head_dim = 512`
- `attention_k_eq_v = true`
- `sliding_window = 1024`
- `layer_types = [sliding_attention x5, full_attention x1] * 10`
- `max_position_embeddings = 262144`
- `use_bidirectional_attention = "vision"`
- `use_cache = true`
- `hidden_size_per_layer_input = 0`
- `enable_moe_block = false`

### 2.3 文本层的关键特点

#### 2.3.1 交替的 sliding / full attention

Gemma4 不是纯 causal full attention，而是 60 层里循环出现：

- 5 层 `sliding_attention`
- 1 层 `full_attention`

这意味着导出时必须同时支持两种 mask：

- `sliding_attention_mask`
- `full_attention_mask`

并且在 wrap 后的 `TextModel.forward()` 中，**每一层要按自己的 `layer_type` 选择对应 mask**。

#### 2.3.2 full attention 与 sliding attention 的 head 配置不同

这是 Gemma4 适配里最容易踩坑的点：

- sliding 层使用：
  - `head_dim = 256`
  - `num_key_value_heads = 16`
- full 层使用：
  - `global_head_dim = 512`
  - `num_global_key_value_heads = 4`

因此：

1. **不同层的 KV cache shape 不统一**；
2. 不能直接套用 `BaseLLMModel/KVCacheMixin` 里“所有层统一 `kv_cache_shape`”的默认假设；
3. Gemma4 需要**按 layer_type / layer_idx 分配 cache**。

#### 2.3.3 Q / K / V 的额外归一化

Gemma4 在 attention 里有：

- `q_norm`
- `k_norm`
- `v_norm`

其中：

- `q_norm` / `k_norm` 是带 scale 的 `Gemma4RMSNorm`
- `v_norm` 是 `with_scale=False` 的 RMSNorm 变体

这意味着 wrap 时不能只包一层普通 `RMSNorm`，而需要区分：

- 带权重缩放的 RMSNorm
- 只做归一化、不乘权重的 RMSNorm

#### 2.3.4 RoPE 也分 sliding / full 两套参数

`rope_parameters` 中：

- `sliding_attention` 使用默认 RoPE，`rope_theta = 10000`
- `full_attention` 使用 proportional RoPE，`rope_theta = 1e6`

因此 wrap 时不能像普通 LLM 一样只缓存一套 `cos/sin`：

- 至少要缓存一套 `sliding_attention` 的 `cos/sin`
- 再缓存一套 `full_attention` 的 `cos/sin`

并在 `layer_type` 维度上做路由。

#### 2.3.5 本 checkpoint 没有 per-layer input 与 MoE 复杂度

这点反而是利好：

- `hidden_size_per_layer_input = 0`
- `enable_moe_block = false`

因此本次适配时：

- 可以跳过 per-layer residual embedding 分支；
- 可以跳过 MoE router / expert 分支；
- 文本部分主要难点集中在 **双 attention 类型 + 双 cache 形状 + 双 RoPE 参数**。

## 三、输入、输出、cache、sliding window 机制

### 3.1 输入张量组织

Gemma4 的 LLM 主输入不是纯 `input_ids`，而是最终送进 text model 的：

- `inputs_embeds`
- `position_ids`
- `attention_mask`（实际是按 layer_type 切成 dict）
- `past_key_values`

在多模态路径下，前处理过程是：

1. tokenizer/processor 先把 `<|image|>` 占位符扩展为一段 image soft token；
2. `vision_tower` 对图像 patch 编码；
3. `embed_vision` 将视觉特征投影到文本空间；
4. 用 `masked_scatter` 将 image soft token 位置替换为 `image_features`；
5. 将得到的 `inputs_embeds` 送入 `language_model`。

### 3.2 图像 token 的组织方式

Gemma4 processor 的图像侧组织逻辑是：

1. 图像会做 **保持宽高比的 resize**；
2. 按 `patch_size = 16` 切 patch；
3. 经过 vision encoder；
4. 再经 pooler 按 `pooling_kernel_size = 3` 做空间池化；
5. 最终每张图得到 `vision_soft_tokens_per_image = 280` 个 soft token。

因此文本里真正插入的不是单个 `<|image|>`，而是：

```text
<boi> + 280 个 image soft token + <eoi>
```

在 processor 里，这个过程通过 `mm_token_type_ids` 辅助构造：

- text token：0
- image token：1
- video token：2（当前可不落）
- audio token：3（当前 checkpoint 未启用）

### 3.3 bidirectional attention for vision tokens

Gemma4 文本模型配置里：

```text
use_bidirectional_attention = "vision"
```

含义是：

- 文本 token 仍然 causal；
- 同一组 vision soft token 内部允许双向可见；
- vision token 可以看见它之前的文本/视觉上下文；
- 但不能随意越过分组边界看未来 token。

官方实现里，这部分是通过：

- `mm_token_type_ids`
- `token_type_ids_mask_function(...)`
- `create_causal_mask_mapping(...)`

共同完成的。

对 Merak 而言，这里有两个可选实现路径：

1. **复用官方 mask 构造逻辑**，在 preprocess 阶段直接生成 `full_attention_mask` + `sliding_attention_mask`；
2. 在 wrapper 里重写一版更适合 trace 的 mask 生成逻辑。

建议走 **方案 1**：把 mask 前移到 preprocess 阶段，wrapper 只消费已生成好的 mask，避免在 FX trace 中引入复杂 Python 分支。

### 3.4 cache 机制

Gemma4 使用 `past_key_values`，但和仓库里现有大多数文本模型不同：

- sliding 层 cache 只需要保留 `sliding_window=1024` 的局部窗口（加当前 chunk）
- full 层 cache 需要保留全上下文
- full 层和 sliding 层的 head_dim / kv_heads 不同，因此 cache shape 不一致

所以 Gemma4 的 cache 管理不能直接照搬：

- `xhmodel_merak/xh_llm/kv_cache_mixin.py::KVCacheMixin`

需要新增一套 **heterogeneous KV cache allocator**，至少要支持：

- `per_layer_k_shapes: list[list[int]]`
- `per_layer_v_shapes: list[list[int]]`
- 输入输出顺序与 export cfg 一一对齐

### 3.5 输出

最终输出仍然是标准自回归 logits：

- prefill：`[B, chunk_len, vocab_size]`
- decode：`[B, 1, vocab_size]`

默认建议在导出时仅保留最后一个 token 的 logits（`num_logits_to_keep = 1`），与现有 Merak 文本模型保持一致。

## 四、需要补哪些 wrap

Gemma4 想做到“整个图可 trace”，至少要补下面几类 wrap。

### 4.1 文本分支最小 wrap 集

建议新增 `xhmodel_merak/xh_llm/models/gemma4/_llm_model_impl.py`，至少覆盖：

1. `Gemma4RMSNorm`
2. `Gemma4TextRotaryEmbedding`
3. `Gemma4TextAttention`
4. `Gemma4TextDecoderLayer`
5. `Gemma4TextModel`
6. `Gemma4Model`
7. `Gemma4ForConditionalGeneration`

其中最关键的是 `Gemma4TextAttention`：

- 需要区分 `sliding_attention` / `full_attention`
- 需要根据 layer_type 使用不同的 `head_dim`
- 需要走不同 RoPE 缓存
- 需要消费不同形状的 past k/v cache
- 需要 `repeat_interleave` 展开 KV group
- 需要将 mask 直接加到 attention logits 再 `softmax`

### 4.2 视觉分支最小 wrap 集

建议新增 `xhmodel_merak/xh_llm/models/gemma4/_vision_model_impl.py`，至少覆盖：

1. `Gemma4VisionPatchEmbedder`
2. `Gemma4VisionEncoderLayer`
3. `Gemma4VisionModel`
4. `Gemma4MultimodalEmbedder`

视觉侧比 Qwen3.5 更简单：

- 没有 M-RoPE 三维 index 逻辑；
- patch position 直接是二维 `(x, y)`；
- pooler 做的是规则空间池化。

这意味着视觉侧复用难度不高，**可参考 `qwen3_5_vision_model.py` 的工程组织方式，但实现逻辑更接近 Gemma4 官方源码本身**。

### 4.3 preprocess 也需要专门实现

建议新增 `xhmodel_merak/xh_llm/models/gemma4/data_preprocess.py`，负责：

1. `input_ids -> inputs_embeds`
2. image placeholder 与 `image_embeds` 对齐替换
3. `position_ids` 生成
4. `mm_token_type_ids` 保留
5. 同时生成：
   - `full_attention_mask`
   - `sliding_attention_mask`
6. 将按层 cache list 展平成导出输入 tuple

Gemma4 的 preprocess 不能直接复用 `BaseLLMInputProcessor`，因为现有基类只考虑：

- 单一注意力 mask
- 单一 KV cache shape
- 纯文本 causal attention

### 5.2 必须注册的点

#### 模型注册

参考 `qwen3_5` / `qwen3_vl`：

- 文本主模型：

```python
@register_llm_model("Gemma4ForConditionalGeneration")
```

- 视觉辅助模型：

```python
@register_llm_model("Gemma4ForConditionalGeneration_visual", master=False)
```

#### wrapper 注册

在 `_llm_model_impl.py` / `_vision_model_impl.py` 中，通过：

- `XHLLM_TRACEABLE_MODULES.register_module(...)`

将 Gemma4 的 HF module 映射到可 trace 的 dynamic wrapper。

#### AutoConfig / AutoModel 注册

因为当前环境没有原生 `gemma4`，必须在本地 vendor 后补注册，至少包括：

- `AutoConfig.register("gemma4", Gemma4Config)`
- `AutoModel.register(Gemma4TextConfig, Gemma4TextModel)`
- `AutoModel.register(Gemma4VisionConfig, Gemma4VisionModel)`
- `AutoModelForImageTextToText.register(Gemma4Config, Gemma4ForConditionalGeneration)`

如果不注册，`AutoConfig.from_pretrained(...)` 和 `AutoModelForImageTextToText.from_pretrained(...)` 无法识别本地 checkpoint。

## 七、验证闭环建议

Gemma4 的验证不能只做“首 token 冒烟”，建议照 qwen3_next / qwen3_5 的标准闭环来做。

### 7.1 功能正确性

至少做以下三层对比：

1. **HF vs Wrap**
2. **Wrap vs Frontend**
3. **Frontend vs Quant**

并且同时覆盖：

- prefill 首 token logits
- decode 多步生成结果
- 图文 prompt（不是纯文本）

### 7.2 推荐测试输入

建议固定一张图 + 一个稳定 prompt，例如：

- 图像：`data/images/bee.jpg`（或仓库已有测试图）
- prompt：`Describe this image in detail.`

### 7.3 建议检查项

#### 文本侧

- prefill logits shape
- decode logits shape
- `past_seq_length` 更新是否正确
- sliding / full attention 输出是否无 NaN

#### 视觉侧

- `pixel_values` 预处理后 patch 数是否稳定
- `num_soft_tokens_per_image == 280`
- `image_position_ids` 与 patch 数是否匹配

#### 多模态融合

- `n_image_tokens == image_features.numel() / hidden_size`
- `masked_scatter` 前后形状一致
- `mm_token_type_ids` 保持不丢失

### 7.4 性能验证

Gemma4-31B 体量较大，性能验证建议分开统计：

1. visual 编码耗时
2. llm prefill 耗时
3. llm decode 单步耗时

至少记录：

- prefill tokens/s
- decode tokens/s
- visual 编码平均耗时
- 首次加载 / 二次加载时延

## 八、当前最重要的工程风险

### 风险 1：transformers 版本缺口

- 当前环境没有 `gemma4`
- 必须 vendor 官方实现并补 compat

### 风险 2：KV cache 形状不统一

- sliding 与 full 层 head_dim / kv_heads 不同
- 不能复用统一形状的默认 KVCacheMixin

### 风险 3：vision token 的 bidirectional mask

- Gemma4 不是“图文都 causal”
- 如果 `mm_token_type_ids` 丢失或 mask 生成错误，图文结果会明显跑偏

### 风险 4：visual 与 llm 不能只迁一个

Gemma4 当前 checkpoint 是 image-text-to-text，不能像纯文本模型那样只落 text。

最小可交付必须包含：

1. visual 分支可导出
2. llm 分支可导出
3. image soft token 替换逻辑可工作

## 十、明确的落地建议（结论）

### 结论 1：Gemma4 应按“Merak 多模态模型”来迁，不应按纯文本 LLM 迁

因为当前 checkpoint 本质上是：

```text
Gemma4ForConditionalGeneration = vision_tower + embed_vision + language_model + lm_head
```

所以最合理的模板不是 `qwen3`，而是：

- **Merak 工程骨架**：`qwen3_5`
- **Gemma 系文本 wrap 思路**：`xhquant_llm/gemma3`
- **官方语义基线**：`modeling_gemma4.py`

### 结论 2：第一版实现范围建议锁定“图文”

虽然 tokenizer / processor 里存在 audio / video token 逻辑，但：

- 当前 checkpoint 的 `audio_config = null`
- 用户任务明确模型路径只有 `weights/gemma-4-31B-it`

因此第一版建议只交付：

- image-text-to-text
- 不展开 audio
- video 逻辑仅保持接口兼容，不作为首轮验证范围

### 结论 3：Gemma4 的核心难点不在视觉，而在文本侧双 attention / 双 cache

真正会卡住 trace/export 的关键点是：

1. `sliding_attention` / `full_attention` 双分支

## 最终一句话方案

**Gemma4 在当前仓库里应当按 `xhmodel_merak/qwen3_5` 的多模态工程骨架落地，按 `xhquant_llm/gemma3` 的 Gemma 文本 wrap 思路实现 attention/RMSNorm/cache，再以官方 `modeling_gemma4.py` 作为语义基准，首版只交付 image-text-to-text，优先解决双 attention 类型、异构 KV cache 和 vision bidirectional mask 三个关键问题。**



下一步任务：
1. 既然Gemma4需要transformer 5.5， 那就conda create --name gemma4 --clone xhquant，然后升级transformers到5.5，验证能否直接加载权重并跑通生成。GPU空闲的随便用，一个任务一张卡够了，可以多个任务并行做。
2. xh2model_merak/xh_llm/models/gemma4/ 中gemma4的模型实现就不要拷贝了，transformer 5.5里已经有了。重点是补齐wrap和preprocess。
3. 模型结构方面
  1. rmsnorm变体，需要抽象下，转成标准的rmsnorm加上一些操作
  2. attention mask，我不确定是不是走的你分析的vision 和 text区分对待的的方案，需要你真实构建debug的demo去 debug验证下中间的状态。
  3. 其他按你的分析来做
4. 视觉分支参考qwen3.5来做
5. 实现方面
  1. 视觉部分, 先在debug_scripts，debug完成
  2. 文本部分，先在debug_scripts里实现
  3. 最后在examples_merak/llm/gemma4/里做完整的导出和推理脚本
6. 验证方面，按照你保证 hf -> wrap, wrap -> frontend, frontend -> quant 三层来做，覆盖 prefill 和 decode，覆盖图文 prompt。保证每一步变换的精度都对。
